Local control plane · v0.1.0 · experimental

Governance 一个跑在本机的工程控制面 —— 阶段状态由磁盘上的产物推导，gate 决定只能追加，不能改写。

大多数 AI 编码工具优化的是产出速度。这个东西优化的是另一件事：你能不能证明某个阶段真的发生过。 它从你的 Markdown 工作区读出事实，推导出九个阶段的状态，把需要人拍板的地方变成 gate，然后只做一件事 —— 把每个决定原样记下来。

三条不变量

Invariant 01

状态派生，不可声明

一个阶段不能"声称"自己完成 —— 它产出的东西存在，才使它完成。这就是看板不会变成第二个真相来源的原因。

Invariant 02

决定追加，不可覆写

通过 / 退回 / 跳过 / 强制通过，各写一行。强制通过必须写理由（override），因为它是唯一一种可以违背证据的结论。

Invariant 03

缺口报告，不可抹平

下游有产物、上游没满足 —— 阶段报 active 并挂 crossed 警告。一个能检测缺口却把缺口吸收掉的 gate，看起来像治理，实际在放行它存在的意义所要阻止的事。

还有第零条：整个产品里没有任何百分比。九个阶段上的一个百分比，暗示了一种这个环路并不具备的精度。只显示离散状态。

产品形态

三个命令

scan读工作区，打印阶段与告警；--json 给机器读
serve本地 UI + API，前台运行
advance规划下一阶段；默认 dry run，--execute 才真的启动

界面上有

  • Portfolio — 多仓库总览，谁被 gate 卡住一眼看到
  • Pipeline rail — 九阶段 + 对应 skill；停用或未安装直接标出
  • Slice board — 票按阻塞图深度排成列，无需手工排序
  • Gate 面板 — 通过 / 退回 / 跳过，各带证据指针
  • Inbox — 还欠人一个决定的地方
  • Settings — agents / skills / MCP / git / automation

新项目：一句模糊的话进，一份 PRD 出

idea → rounds → prd
  • 想法原样送入，不做整理 —— 模糊本身就是原料。
  • 中间那一步由 /grill-with-docs 这个 skill 驱动。应用里没有一行"该怎么提问"的逻辑，提示词只说明读哪个文件、要什么格式回来。
  • 每轮返回问题 + agent 自己会给出的答案，全部同意就是一键通过。
  • 前沿没清空之前拒绝生成 PRD —— 提前冻结会锁死那些还没被问到的问题。
  • 每个 effort 一条会话，关电脑、第二天回来，从同一轮继续。
  • 每一轮都是磁盘上的产物，不是一个正在消失的聊天窗口。

边界：明确不做什么

这些不是"还没做"，是设计本身。去掉任何一条，这个产品的性质就变了。

边界原因
只监听 loopback没有网络面，所以也不需要认证；不会有第二个用户。
前台运行，无定时器，无文件监听进程退出就什么都不在跑。否则它会变成一个后台自己刷新的看板 —— 那就成了它不该是的托管服务。
只写 effort 自己的 .scratch/服务端从不接受客户端传来的路径；解析后二次校验仍在工作区内，并有路径穿越测试。
不制造新的真相来源Markdown 永远权威，每次请求重读、不缓存。过期的看板比慢的看板更糟。
不执行部署部署在这里被批准、被记录；执行留在外面。

已知缺口 open

  • GitHub 镜像 — 延后；将来也只能单向出，不能成为第二权威
  • SLA 超时升级 — 没有定时器可挂，字段存着，不假装在跑
  • 运行历史进 UI — 日志在写，视图还没读
  • 并行调度 — maxParallel 存了、显示了，一次仍只跑一个阶段
  • 真实 CLI 本机不可执行 — 沙箱拦截；探针分别报告「装了吗」和「能跑吗」

30 秒讲法

这是一个本地的工程控制面。它不帮你写代码更快，它帮你证明流程真的走过了。 九阶段环路，每个阶段的状态是从磁盘上的产物推导出来的，不是点出来的；每个 gate 的批准只能追加进日志，改不了。 所以它永远不会变成第二个和现实不一致的看板 —— 它甚至在你自己的仓库里找出过一处"没做设计就直接开了票"的真实缺口，而且只是报告，没有替你抹平。

两分钟演示，不需要任何凭证
